# End-to-End Full Part Simulation Implementation Plan

## 1. Purpose

This document defines the implementation plan for turning H-eduware from a starter-circuit simulator into a broad hardware simulation system that can accept student requests over the full visual part library.

The product goal is:

> Students should be able to ask for circuits using the parts available in the app, and H-eduware should either produce a grounded, validated, rendered, runnable simulation or clearly explain the exact missing support/safety blocker.

This means the system should not restrict students to five starter capabilities. The current starter set should remain as regression coverage, but the target architecture must support every available part through a consistent context, validation, rendering, and simulation pipeline.

### 2.2.5 Current Placement Behavior

Hardware positions in the 3D simulation are currently determined by the server-side render plan:

- If a `CircuitSpec` component already has an explicit `position`, that position wins.
- Otherwise `compileRenderPlan()` derives deterministic default positions from render footprints and the breadboard grid.
- Breadboard, Arduino, and selected larger parts have fixed default locations.
- Breadboard-compatible parts are packed inside the breadboard footprint, snapped to the modeled breadboard grid, and checked for out-of-bounds or overlap risks.
- Wire endpoints are computed as `part.position + footprint.pinAnchors[pin]`, so pin anchors, not LLM prose, determine visible wire attachment points.

For the full-part-library goal, placement should be tightened further: live agent drafts should not be trusted to hand-author arbitrary positions. The safer target is to let the LLM choose logical parts and connections, while a deterministic placement resolver owns physical positions, grid snapping, collision checks, and render DRC.

### 2.3 Current Blocking Gap

The main gap is not that the agent cannot chat. The gap is that the agent cannot yet guarantee a full app-runnable artifact for the entire part library.

Today, live success can stop too early:

```txt
validationReport.status === valid
```

But the real app success condition is closer to:

```txt
contextCoverage.synthesisEligibility === eligible
validationReport.status === valid
renderPlan.parts.length > 0
simulationPlan.status === valid
simulationPlan.currentPaths or expectedStates are meaningful
no simulation-blocking render DRC warning exists
frontend canBuildAgentResult(result) === true
```

This distinction matters because a circuit can be electrically valid but still fail the existing Run track if render DRC or simulation gating blocks it.

## 3. Key Product Decision

All 132 visual parts should become first-class context layer entities.

However, "supported" must be split into tiers. Every part can be understood by the agent, but not every part can immediately be simulated with the same confidence.

The system must avoid both extremes:

- Too restrictive: refusing student ideas just because they mention a non-starter part.
- Too permissive: generating fake wiring or fake simulation for parts without deterministic support.

The target behavior is:

```txt
Every visual part is context-known.
Only validated combinations become simulation-ready.
Unsupported or unsafe combinations are explained, not fabricated.
```

## 4. Support Tier Model

Add explicit support tiers for parts, capabilities, and generated circuit artifacts.

### 4.1 Part Support Tiers

`catalog-only`

- Exists in `src/partLibraryData.js`.
- May be shown in the UI.
- Agent cannot yet reason about pins or wiring.

`context-known`

- Agent knows the part identity, category, common names, aliases, typical use, risk class, and common alternatives.
- Agent can answer questions about the part.
- Agent cannot generate build-ready wiring yet.

`pin-known`

- Pin names, pin roles, voltage domain, protocols, and common aliases are modeled.
- Agent can propose high-level connections, but deterministic validation may still block build/run.

`render-ready`

- Render footprint exists.
- Pin anchors exist.
- The part can appear in a generated visual circuit.

`validation-ready`

- Deterministic validation rules exist for the part family.
- The server can reject wrong pins, missing power, missing ground, unsafe topology, missing passives, and known forbidden connections.

`simulation-ready`

- Simulation primitive exists.
- Current path or state model exists.
- UI control/state mapping exists where relevant.
- Render overlays exist.
- Browser-visible E2E evidence exists.

### 4.2 Capability Support Tiers

Capabilities should use the same staged model:

- `context-known`
- `render-ready`
- `validation-ready`
- `simulation-ready`
- `unsafe-blocked`

The old `supported/planned/unsupported` labels can remain as public summaries, but internally they should map to this more precise tier system.

## 5. Target End-to-End Architecture

```txt
Student request
  -> requirement analysis agent
  -> context packet builder
  -> part/capability candidate retrieval
  -> circuit planner LLM
  -> deterministic schema parse
  -> deterministic part/pin resolver
  -> netlist compiler
  -> safety validator
  -> topology validator
  -> render compiler
  -> render DRC
  -> simulation compiler
  -> simulation quality gate
  -> frontend confirm/build/run
  -> browser-visible E2E verification
```

The LLM is a planner and explainer. It must not be the truth authority.

Truth authority belongs to:

- canonical part registry
- source claims
- pin resolver
- topology templates
- validation engine
- render DRC
- simulation planner
- frontend E2E gates

### 5.1 Context Packet Shape

The context layer does not need a deeply hierarchical prompt structure. The preferred shape is a flat canonical index plus selective bundle expansion.

- Keep the always-loaded routing surface compact: part ids, aliases, families, support tiers, route ids, and blocker summaries.
- Expand detailed evidence only after requirement analysis selects candidate capabilities: pin maps, topology templates, source claims, render footprints, simulation primitives, and validator rules.
- Do not load build/run bundles for casual conversation, open-ended ideation, or unsupported explanation-only turns.
- When the student names a concrete hardware family, prune generic sibling bundles so the quality gate does not see conflicting routes. For example, SPI display requests should not carry the generic OLED display bundle unless the request also needs it.
- Speed comes from one compact flat index; reliability comes from selected support bundles and deterministic validation.

## 6. LLM Role

Additional LLM use is useful, but only in bounded places.

### 6.1 Good LLM Responsibilities

- Interpret student intent from natural language.
- Identify requested inputs, outputs, behaviors, controller assumptions, and ambiguity.
- Suggest part candidates from the available library.
- Draft a candidate `CircuitSpec`.
- Explain validation failures in student-friendly language.
- Propose safe alternatives when a requested circuit cannot run.

### 6.2 Bad LLM Responsibilities

The LLM must not make final decisions about:

- part support status
- electrical safety
- hidden shorts
- current paths
- Run availability
- voltage/current limits
- whether a simulation is valid

## 9. Validation Engine Implementation

### 9.1 Pin Resolver

Implement deterministic pin alias resolution.

Examples:

- `VCC`, `VIN`, `5V`, `+`, `전원`
- `GND`, `ground`, `-`, `0V`, `접지`
- `SDA`, `A4`, `data`, `데이터`
- `SCL`, `A5`, `clock`, `클럭`
- `AO`, `A0`, `analog`, `아날로그`
- `DO`, `D2`, `digital`, `디지털`

The LLM can suggest pins, but the resolver must canonicalize or reject them.

### 9.2 Topology Templates

Move from named demos to topology templates:

- controller digital output -> current-limited load -> ground
- controller digital input -> switch -> ground with internal pull-up
- analog voltage divider -> analog input
- analog threshold -> digital output load
- I2C controller -> I2C module with power and ground
- SPI controller -> SPI module with CS
- PWM output -> actuator signal
- motor driver input -> motor load with separate supply
- power source -> regulator -> rail

### 9.3 Safety Validators

Validation should block:

- mains voltage on breadboard
- high-current motor directly from GPIO
- relay load side treated as safe low-voltage simulation without load definition
- LiPo/9V misuse on 5V-only modules
- missing current limit for LEDs
- missing common ground
- mixed incompatible voltage domains
- direct power-ground short
- hidden breadboard node/rail conflicts

## 10. Render Implementation

### 10.1 Footprint Strategy

Do not hand-model every shape immediately. Use footprint tiers:

- generic module board
- two-pin through-hole
- three-pin sensor/module
- four-pin I2C module
- multi-pin IC/DIP
- motor/actuator block
- power connector
- display panel

Each visual part can map to a generic footprint first, then receive a richer custom footprint later.

### 10.2 DRC Rules

Render DRC remains part of the quality gate.

Simulation must be blocked when:

- endpoint anchor is missing
- component required in a current path is not rendered
- hidden physical node conflict exists
- hidden rail conflict exists
- critical footprint is missing

Non-blocking render warnings can still allow simulation:

- minor label overlap
- generic footprint fallback
- non-critical grid misalignment where logical endpoints remain explicit

## 11. Simulation Engine Implementation

### 11.1 SimulationPlan Quality Gate

Create a single server-side function:

```ts
function isBuildRunnable(result: AgentRunResult): BuildRunnableReport
```

It should mirror frontend `canBuildAgentResult` and add diagnostic reasons:

- context ineligible
- validation invalid
- render empty
- simulation invalid
- missing current path
- missing expected state
- render DRC blocked simulation
- unsupported/unsafe

The agent repair loop must use this report, not only `validationReport.status`.

Current solver-gate contract:

- `buildRunnableReport` remains the strict gate for Run, share, current animation, and build-ready claims.
- `solverGateResult.visibleSimulation` controls whether the student may see a scene.
- clarification-only, meta, and non-hardware unsupported turns remain no-scene.
- unsupported hardware specs may render diagnostic context while keeping Run/share/build-ready blocked.
- missing exact footprints may render `placeholder_part_simulation`; placeholder geometry is visible evidence, not build-ready evidence.
- unsafe or physically invalid requests may be replaced with `safe_equivalent_simulation`; the original request remains blocked and the equivalent must be labeled.

### 11.2 Repair Loop Inputs

Feed these failures back into the agent as repair reasons:

- `LED_WITHOUT_RESISTOR`
- `COMMON_GROUND_MISSING`
- `PIN_NOT_FOUND`
- `CONTEXT_CANDIDATE_PART_NOT_ALLOWED`
- `MISSING_RENDER_FOOTPRINT`
- `BREADBOARD_PHYSICAL_NODE_CONFLICT`
- `BREADBOARD_CONTINUITY_CONFLICT`
- `BREADBOARD_RAIL_CONFLICT`
- `SIMULATION_PATH_NOT_VALIDATED`
- `SIMULATION_ENDPOINT_ANCHOR_MISSING`
- `simulationPlan.status !== valid`

### 11.3 Simulation Output Types

Not every simulation must be current dots.

Support multiple educational simulation surfaces:

- current path animation
- digital state toggle
- analog slider
- threshold marker
- display readout
- sensor value readout
- PWM pulse indicator
- servo angle arc
- bus activity pulses
- blocked/fault overlay

## 12. Agent Workflow Changes

### 12.1 Requirement Analysis

Keep the requirement analysis agent, but make its output stricter:

- requested input parts
- requested output parts
- behavior trigger
- behavior action
- required physical parts
- candidate simulation family
- ambiguity
- safety risk
- desired artifact type

### 12.2 Context Packet

The context packet must include:

- selected visual parts
- canonical part candidates
- part support tiers
- family support tiers
- validation templates
- simulation family contracts
- render footprint availability
- source claim status
- route blocker reasons

### 12.3 Circuit Planner

The LLM planner should produce multiple candidates when useful:

- preferred circuit
- simpler supported alternative
- blocked circuit explanation

But only candidates that pass deterministic quality gates can reach confirm/build/Run.

### 12.4 Final Response

Student-facing messages should avoid internal terms like:

- context packet
- support bundle
- canonical context
- valid synthesis
- structured output

They should say:

- "이 부품은 앱에는 있지만 아직 배선 검증/시뮬레이션 자료가 부족해요."
- "이 회로는 실행할 수 있어요."
- "이 연결은 위험해서 실행하지 않을게요."
- "대신 현재 부품으로 가능한 안전한 회로는 이것이에요."

## 13. E2E Acceptance Criteria

### 13.1 Context Coverage E2E

For all 132 parts:

- part appears in crosswalk
- part has support tier
- part has category/family
- context packet can mention the part without hallucinating support
- unsupported or unsafe part has a blocker reason

### 13.2 Simulation-Ready E2E

For each simulation-ready family:

1. Student enters a natural request.
2. Requirement analysis extracts input/output/behavior.
3. Context packet selects correct parts/family.
4. Agent drafts a circuit.
5. Validator passes.
6. Render plan has parts/connections.
7. Simulation plan is valid.
8. Confirm button appears.
9. Build progress runs.
10. PCB renders nonblank.
11. Run button animates state/current.
12. Inspector can answer a grounded question.

### 13.3 Blocked E2E

For blocked requests:

1. Student asks for unsupported or unsafe hardware.
2. No build/confirm button appears.
3. No fake render/current path is produced.
4. The assistant explains the blocker.
5. A safe/context-supported alternative is offered.
